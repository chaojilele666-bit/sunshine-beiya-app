# 第一部分：项目当前总体框架

## 1. 项目定位

阳光北亚家政平台是一套面向客户、家政员和内部管理人员的家政服务撮合与业务管理系统。

项目目标是将阳光北亚现有线下家政业务逐步数字化，主要解决：

- 客户提交家政服务需求；
- 平台管理客户、家政员和服务项目；
- 后台审核需求并安排家政员；
- 家政员查看和执行服务任务；
- 平台跟踪订单与服务进度；
- 服务完成后进行评价、回访和经营数据沉淀。

本项目当前**不建设线上支付系统**，不接入微信支付、支付宝支付、线上退款、分账或资金清算能力。

如业务需要记录费用，只记录：

- 服务报价；
- 最终服务金额；
- 线下结算状态；
- 结算备注。

资金实际支付在线下或平台外完成。

---

## 2. 核心业务闭环

```text
客户注册/登录
→ 浏览服务内容
→ 填写地址、时间和服务需求
→ 提交服务申请/订单
→ 后台联系客户并确认需求
→ 后台人工选择和分配家政员
→ 家政员确认任务
→ 家政员上门服务
→ 后台/家政员更新服务进度
→ 服务完成
→ 线下结算状态登记（如需要）
→ 客户评价与平台回访
→ 沉淀客户、家政员和服务数据
```

第一版优先采用**后台人工派单**，暂不建设自动匹配、抢单或复杂推荐系统。

---

## 3. 用户与角色体系

统一用户体系管理以下角色：

- 客户 `customer`
- 家政员 `worker`
- 管理员 `admin`
- 经理 `manager`

当前相关数据模型：

- `users`
- `customer_profiles`
- `worker_profiles`
- `addresses`

### 客户主要能力

- 注册和登录；
- 管理个人资料和服务地址；
- 浏览服务内容；
- 提交家政服务需求；
- 查看服务进度；
- 取消尚未开始的需求；
- 对已完成服务进行评价。

### 家政员主要能力

- 查看个人资料和认证状态；
- 查看平台分配的服务任务；
- 确认或反馈任务；
- 查看服务地址、时间和需求；
- 更新到达、服务中、完成等状态；
- 查看历史服务记录和评价。

### 管理员/经理主要能力

- 管理客户资料；
- 管理家政员资料和认证；
- 管理服务分类和服务项目；
- 查看、确认、分配和调整服务订单；
- 记录客户沟通情况；
- 处理取消、改期、投诉和回访；
- 查看运营数据和审计记录。

---

## 4. 服务体系

服务采用“服务分类 + 具体服务项目”的两级结构。

当前服务分类示例：

- 日常保洁；
- 深度清洁；
- 长期家政。

当前服务项目示例：

- 两小时日常保洁；
- 厨房深度清洁；
- 长期家政面谈。

当前相关数据模型：

- `service_categories`
- `service_items`
- `worker_service_items`

服务项目可以记录：

- 服务名称；
- 服务介绍；
- 参考价格；
- 计价单位；
- 预计服务时长；
- 是否启用。

参考价格仅用于展示和报价，不代表平台已经具备线上收款能力。

---

## 5. 家政员管理体系

平台不仅保存家政员名单，还需要逐步形成家政员服务能力档案。

家政员资料包括：

- 姓名和联系方式；
- 从业年限；
- 服务城市和区域；
- 个人简介；
- 认证状态；
- 可提供的服务项目；
- 是否可接任务；
- 已完成服务数量；
- 客户评分；
- 历史任务和评价。

第一版由后台管理人员维护家政员资料、认证状态和服务能力。

---

## 6. 订单与服务任务体系

订单/服务申请是平台的核心业务对象，连接：

- 客户；
- 服务项目；
- 服务地址；
- 预约时间；
- 客户需求备注；
- 被分配的家政员；
- 服务进度；
- 报价与线下结算备注；
- 评价和回访结果。

### 建议的订单状态

当前数据库状态仍需进一步调整。推荐第一版采用更符合人工派单业务的状态：

- `submitted`：客户已提交；
- `contacting`：平台正在联系确认；
- `confirmed`：需求已确认；
- `assigned`：已分配家政员；
- `accepted`：家政员已确认；
- `in_progress`：服务中；
- `completed`：已完成；
- `cancelled`：已取消。

可选异常状态：

- `reschedule_required`：需要改期；
- `complaint`：存在投诉或售后问题。

状态变更必须记录操作人、变更前状态、变更后状态、时间和备注。

---

## 7. 结算范围

当前项目不做线上支付。

可以保留轻量级线下结算记录，但不能设计成支付网关。

建议记录字段：

- `quoted_amount_cents`：平台报价；
- `final_amount_cents`：最终金额；
- `settlement_status`：未登记、待线下结算、已线下结算、无需结算；
- `settlement_method_note`：现金、转账或其他备注；
- `settled_at`：结算登记时间；
- `settlement_note`：补充说明。

明确不开发：

- 微信支付；
- 支付宝支付；
- 在线退款；
- 平台分账；
- 支付回调；
- 对账和资金清算。

当前数据库中的 `payments` 表与最新产品方向不一致：

- 从本次更新起停止扩展；
- 新功能不得依赖该表；
- 后续数据库重构时删除，或替换为简单的线下结算记录结构。

---

## 8. 评价、投诉和回访

客户可以在服务完成后评价家政员和本次服务。

评价内容包括：

- 星级评分；
- 文字评价；
- 服务标签；
- 是否愿意再次选择该家政员。

后台还应支持：

- 客户投诉记录；
- 处理进度；
- 处理结果；
- 服务完成后的回访；
- 回访备注。

投诉和回访建议后续建立独立数据模型，不应全部塞入订单备注。

---

## 9. 后台与审计体系

所有重要后台操作必须写入审计日志，包括：

- 修改客户资料；
- 修改家政员资料或认证状态；
- 创建、修改或停用服务项目；
- 确认、派发、改期或取消订单；
- 修改订单金额或线下结算状态；
- 处理投诉和回访；
- 修改用户权限。

审计日志至少记录：

- 操作人；
- 操作行为；
- 操作对象类型；
- 操作对象 ID；
- 修改前数据摘要；
- 修改后数据摘要；
- 操作时间；
- 操作备注。

# 第二部分：当前改进重点

## P0：开发前必须补齐

1. **明确第一版 MVP 范围**
   - 第一版只完成客户提交需求、后台确认派单、家政员执行、订单跟踪和评价回访。
   - 不开发线上支付、自动派单、抢单、复杂推荐和会员体系。

2. **重新设计订单状态**
   - 当前状态缺少客户提交、平台联系、已派单和家政员确认等关键阶段。
   - 必须建立严格的状态流转规则。

3. **明确三端页面清单**
   - 客户端；
   - 家政员端；
   - 管理后台。

4. **建立角色权限表**
   - 明确每种角色可以读取和修改哪些资源。
   - 权限必须在后端校验，不能只依赖前端隐藏按钮。

5. **建立 API 契约**
   - 统一请求、响应、错误码、分页、金额和时间格式。

6. **清理支付设计冲突**
   - 停止开发 `payments` 表相关功能；
   - 后续改为线下结算记录或直接并入订单扩展字段。

## P1：第一版开发阶段补齐

1. 家政员认证资料和审核流程；
2. 客户需求确认和电话沟通记录；
3. 人工派单与家政员确认流程；
4. 改期、取消和异常订单处理；
5. 投诉和回访数据模型；
6. 敏感信息保护、数据脱敏和操作审计；
7. 数据库 migration 和自动化测试。

## P2：第一版稳定后再考虑

1. 自动匹配或智能推荐家政员；
2. 家政员排班和可用时间；
3. 优惠券、会员和营销活动；
4. 经营数据分析；
5. 企业微信、短信或小程序消息通知；
6. 多门店、多城市和区域管理。

# 第三部分：强制更新记录规则

## 1. 修改前

每次开始修改前，开发人员或 AI Agent 必须：

1. 阅读本文件中的“项目当前总体框架”；
2. 阅读最近的更新记录；
3. 确认本次修改是否符合当前项目定位；
4. 确认是否影响数据库、接口、前端、权限或业务流程；
5. 如发现需求与现有设计冲突，必须先在任务说明中指出，不能直接擅自实现。

## 2. 修改后

每次修改完成后，必须在本文件末尾追加一条记录，禁止覆盖或删除历史记录。

每条记录必须包含：

```markdown
## YYYY-MM-DD HH:mm（Asia/Shanghai）

### 本次目标
- 为什么进行这次修改。

### 修改内容
- 新增了什么；
- 修改了什么；
- 删除或停用了什么。

### 影响范围
- 前端：
- 后端：
- 数据库：
- 文档：

### 验证情况
- 执行了哪些测试或检查；
- 哪些内容尚未验证。

### 当前项目状态
- 修改后项目已经具备什么；
- 仍然缺少什么；
- 下一步建议是什么。
```

## 3. 禁止事项

- 禁止只改代码、不更新日志；
- 禁止使用“优化了一些内容”这种模糊描述；
- 禁止删除以前的日志记录；
- 禁止在未说明影响范围的情况下大规模重构；
- 禁止恢复或扩展线上支付功能，除非项目负责人明确改变产品方向；
- 禁止把尚未完成或尚未测试的功能写成“已完成”。
